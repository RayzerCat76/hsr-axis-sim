Task ID: HSR-AXIS-001H
Reasoning: HIGH

You are continuing the permanent Python project for a Honkai: Star Rail inspired action-axis simulator.

The previous accepted task was HSR-AXIS-001G, which added the event hook / trigger system MVP.

Do not scrape Huroka, Yatta, HoneyHunter, Bilibili, or any external website in this task.
Do not implement AI axis search in this task.
Do not implement every real character in this task.
Do not rewrite the simulator core unless a small compatibility change is strictly required and covered by tests.

Goal:
Add a data-driven character / skill schema MVP so the simulator can load simplified characters, skills, actions, and triggers from JSON files instead of hard-coding everything inside replay action specs.

Why this matters:
The project will eventually import character data from external databases such as Huroka/Yatta, but external raw data must first map into our own stable schema. This task creates that internal schema and loader.

Required new structure:

hsr_axis_sim/
  data/
    sample_characters/
      bronya_like.json
      seele_like.json
      generic_enemy.json
    sample_teams/
      bronya_seele_team.json
    golden_replays/
      data_loaded_bronya_seele_mvp.json
  sim/
    data_schema.py
    data_loader.py
  tests/
    test_data_schema.py
    test_data_loader.py
    test_data_loaded_replay.py

Use dataclasses or Pydantic, whichever is consistent with the existing project style. If Pydantic is not already a project dependency, prefer dataclasses plus explicit validation so the project stays lightweight.

Required schema concepts:

1. CharacterSpec
   Fields:
   - id
   - name
   - team default or suggested team
   - element optional
   - path optional
   - base_stats
   - skills
   - triggers optional

2. BaseStatsSpec
   Fields:
   - hp
   - atk
   - defense
   - base_speed
   - max_energy
   - crit_rate
   - crit_dmg
   - dmg_bonus
   - max_toughness optional
   - weaknesses optional

3. SkillSpec
   Fields:
   - id
   - name
   - skill_type, such as basic / skill / ultimate / talent / technique / special
   - target_type, such as self / single_ally / single_enemy / all_enemies / selected
   - sp_delta or explicit SP effects
   - energy_delta or explicit energy effects
   - ends_turn
   - effects

4. TeamSpec
   Fields:
   - id
   - name
   - unit_refs
   - initial_skill_points
   - max_skill_points

5. UnitBuildSpec or UnitInstanceSpec
   Fields:
   - character_id
   - unit_id
   - team
   - level optional
   - stat_overrides optional
   - initial_energy optional
   - initial_current_av optional
   - initial_hp optional
   - initial_toughness optional

6. TriggerSpec
   Use the existing Trigger fields:
   - id
   - owner_id may be omitted in character-owned trigger templates and filled by loader
   - event_type
   - condition
   - effects
   - max_triggers_per_action
   - enabled

7. EffectSpec
   Must support all existing replay effect types:
   - AddBuff
   - AddDebuff
   - AdvanceAction
   - ChangeSpeed
   - ConsumeEnergy
   - ConsumeSkillPoint
   - DealDamage
   - DealToughnessDamage
   - DelayAction
   - DoesNotEndTurn
   - GainEnergy
   - GainSkillPoint
   - GrantExtraTurn
   - ImmediateAction
   - RemoveBuff
   - RemoveDebuff

Loader requirements:

1. Implement a function to load a CharacterSpec from JSON.
2. Implement a function to instantiate a Unit from a CharacterSpec + UnitInstanceSpec.
3. Implement a function to build a BattleState from a TeamSpec plus character JSON files.
4. Implement a function to construct an Action from a loaded SkillSpec for a specific actor and target list.
5. Character-owned trigger templates must become real Trigger objects with `owner_id` filled as the instantiated unit id.
6. Stat overrides must apply cleanly and only to known stat fields.
7. Unknown effect types, missing required fields, duplicate skill ids, duplicate unit ids, and unknown character ids must raise clear errors.

Sample data requirements:

Create simplified data files only. Do not use copyrighted full official text. Use generic names and minimal numeric values.

1. `seele_like.json`
   - A simplified DPS character.
   - Has a skill that deals fixed or calculated damage to one enemy.
   - Has an on-kill trigger that grants an extra turn.
   - This should use the existing generic trigger system, not hard-coded Python character logic.

2. `bronya_like.json`
   - A simplified support character.
   - Has a skill that gives one selected ally immediate action or action advance according to current engine capabilities.
   - Has a simple damage/buff effect if useful, but keep it minimal.

3. `generic_enemy.json`
   - A simplified enemy unit with HP, toughness, and speed.

4. `bronya_seele_team.json`
   - Instantiates one Bronya-like support, one Seele-like DPS, and one or two enemies.
   - Provides initial SP and initial AV values.

Replay requirement:

Add `data_loaded_bronya_seele_mvp.json`.

This replay should demonstrate that the same kind of Bronya-like + Seele-like flow can be executed using data-loaded skills/actions rather than fully hard-coded replay action definitions.

Acceptable approach:
