3. Add scoring profiles

Add a simple profile abstraction. It can be a dataclass, enum + config, or factory functions, but it must be easy to test.

Required built-in profiles:

A. `generic_kill`
- Backward-compatible with the existing evaluator intent.
- Rewards defeated enemies, enemy HP missing, skill points, alive allies.
- Penalizes global AV and depth.

B. `zero_cycle`
- Strongly rewards defeating all enemies quickly.
- Penalizes global AV more than `generic_kill`.
- Penalizes action count/depth more than `generic_kill`.
- Should still reward damage progress if enemies are not all dead.

C. `damage_race`
- Prioritizes enemy HP missing and defeated enemies.
- Penalizes global AV moderately.
- Does not over-prioritize SP conservation.

D. `survival_safe`
- Rewards alive allies and remaining ally HP.
- Penalizes defeated allies heavily.
- Still rewards enemy progress, but less aggressively than damage_race.

E. `sp_conservative`
- Rewards progress while preserving or gaining skill points.
- Useful for testing resource-aware axis preferences.

Implementation can use profile weights such as:

```python
@dataclass
class ScoreProfile:
    id: str
    defeated_enemy_bonus: float
    all_enemies_defeated_bonus: float
    enemy_hp_missing_weight: float
    global_av_penalty: float
    depth_penalty: float
    skill_point_bonus: float
    alive_ally_bonus: float
    ally_hp_remaining_weight: float
    defeated_ally_penalty: float
```

You may adjust exact field names, but keep them readable and tested.
