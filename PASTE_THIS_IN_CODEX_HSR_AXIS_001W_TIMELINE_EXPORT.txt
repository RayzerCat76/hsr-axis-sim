Task ID: HSR-AXIS-001W
Title: Timeline Snapshot / Static Axis Visualization Export MVP

Codex Reasoning: Medium
ChatGPT Model recommendation: GPT-5.5
Reason: This task is mostly report/data-export work around existing search output. It should not alter timeline, damage, targeting, buff, break, enemy AI, or search semantics. Use GPT-5.5 Thinking only if state snapshot serialization becomes unexpectedly complex.

Context:
We have completed HSR-AXIS-001V. The project now has a CLI scenario runner that can load a JSON search scenario, run beam search, and export text/Markdown/JSON reports.

Current problem:
The current axis report is useful, but it only lists action records. For debugging real Bilibili golden replays and future visual UI work, we need static per-step snapshots showing what the battle state looked like after each axis step.

Goal:
Add a lightweight timeline snapshot/export layer so search reports can show per-step unit state summaries without changing battle mechanics.

Hard scope boundaries:
- Do NOT change battle timeline semantics.
- Do NOT change damage formula semantics.
- Do NOT change break/toughness semantics.
- Do NOT change target legality/action generator semantics.
- Do NOT change beam-search ranking/selection semantics except to carry additional report metadata.
- Do NOT scrape Huroka, Yatta, Bilibili, or any external website.
- Do NOT build a web UI.
- Do NOT generate images/charts.
- Do NOT add external dependencies.

Required feature:
Add static timeline snapshots for the best axis and optionally final beam candidates.

Suggested implementation:

1. Add compact state snapshot dataclasses, likely in a new module such as:

```text
hsr_axis_sim/search/timeline_snapshot.py
```

Suggested dataclasses:

```python
@dataclass
class UnitSnapshot:
    unit_id: str
    team: str
    hp: float
    max_hp: float
    energy: float
    current_av: float
    speed: float
    current_toughness: float | None
    max_toughness: float | None
    is_broken: bool
    is_alive: bool
    buffs: list[str]
    debuffs: list[str]

@dataclass
class BattleSnapshot:
    global_av: float
    skill_points: int
    units: list[UnitSnapshot]
```

Keep the exact fields compatible with the current `Unit` model. If a field does not exist on Unit, do not invent mechanics. Use `getattr(..., default)` carefully where needed.

2. Add snapshot creation helpers:

```python
snapshot_battle_state(state: BattleState) -> BattleSnapshot
```

The snapshot should be deterministic and stable:
- units ordered by current team grouping or existing state order, but choose one and test it.
- floating values should be kept as numbers in JSON export, not preformatted strings.

3. Extend search action records/report objects so each best-axis step can include:

```text
snapshot_before
snapshot_after
```

or at minimum:

```text
snapshot_after
```

Prefer both if it can be done without making search code messy.

Do not store a full deep-copied BattleState in the report. Store only compact snapshot dataclasses/dicts.

4. Update `SearchEngine._child_from_branch(...)` or nearby report-building code so snapshots are captured after actions are applied.

If adding `snapshot_before`, capture it before action execution:
- for normal actions: after `Timeline.next_turn(...)` selects the actor, before the chosen action executes.
- for ultimate/interrupt actions: before `execute_interrupt_action(...)` executes.

If this is too invasive, implement `snapshot_after` first and document the limitation.

5. Update JSON report export.

`search_report_to_dict(report)` should include snapshots in JSON-compatible form.

The JSON report should include, for each axis step, something like:

```json
{
  "step": 1,
  "actor_id": "seele_like",
  "action_id": "skill",
  "target_ids": ["enemy_1"],
  "global_av_before": 0.0,
  "global_av_after": 0.0,
  "skill_points_after": 3,
  "score_after": 102850.0,
  "snapshot_after": {
    "global_av": 0.0,
    "skill_points": 3,
    "units": [
      {
        "unit_id": "seele_like",
        "team": "ally",
        "hp": 1000.0,
        "energy": 30.0,
        "current_av": 69.93,
        "speed": 143.0,
        "is_alive": true
      }
    ]
  }
}
```

Do not require these exact numbers; follow actual state fields.

6. Update Markdown report with a compact optional section.

Add a section after Best Axis, for example:

```markdown
## Timeline Snapshots

### After Step 1

| Unit | Team | HP | Energy | AV | Toughness | Broken | Alive |
|---|---|---:|---:|---:|---:|---|---|
```

Keep it compact. It is okay to include only best-axis snapshots for MVP.

7. Update text report similarly with readable but compact state summaries.

8. CLI integration.

The existing scenario CLI should support an option:

```text
--include-snapshots
```

Recommended behavior:
- Default reports remain concise and similar to 001V.
- If `--include-snapshots` is passed, Markdown/text reports include the timeline snapshot section.
- JSON output may always include snapshots, or may include them only when requested. Pick one behavior, document it, and test it. Prefer always including snapshots in JSON because JSON is for machine consumers.

9. Add/update tests.

Required tests:
- snapshot helper returns stable unit snapshots from a simple BattleState.
- JSON report includes `snapshot_after` for best-axis steps.
- Markdown with snapshots includes `## Timeline Snapshots`.
- Text with snapshots includes a recognizable snapshot section.
- CLI `--include-snapshots --format markdown` works.
- CLI output file with snapshots works.
- Existing scenario runner tests still pass.
- All previous pytest tests must continue to pass.
