Blocking issue
==============

The reviewed registry still has an uncontrolled malformed-binding crash path.

For example, a package-contained Tingyun binding containing:

    "source_atomic_fact_ids": [{"bad": "value"}]

causes Tingyun validation to call `set(source_ids)`, raising:

    TypeError: unhashable type: 'dict'

The registry CLI then prints a Python traceback.

The older Pela validator has the same class of issue because it also performs set operations before validating list member types.

Goal
====

Harden both reviewed binding validators so malformed JSON-compatible values always produce controlled `ValueError` validation failures and never leak `TypeError`, `AttributeError`, or traceback through the reviewed registry CLI.

Required changes
================

1. Harden:

- `hsr_axis_sim/real_bindings/tingyun_ultimate_v0_1.py`
- `hsr_axis_sim/real_bindings/pela_skill_v0_1.py`

2. Before any set conversion, set union, sorting, or dictionary-key construction, validate:

- binding is an object;
- atomic-fact artifact is an object;
- `atomic_facts` is a list;
- every atomic-fact item is an object;
- every `atomic_fact_id` is a non-empty string;
- atomic fact IDs are unique;
- `source_atomic_fact_ids` is a list of unique, non-empty strings;
- `unresolved_atomic_fact_ids` is a list of unique, non-empty strings;
- `unresolved_fields`, where used, is a list of unique, non-empty strings.

3. Malformed values must produce handler-specific `ValueError` messages, for example:

- `Tingyun Ultimate partial binding validation failed: ...`
- `Pela Skill partial binding validation failed: ...`

4. Do not solve this only by broadly catching `TypeError` in the CLI. The validators themselves must be safe and deterministic.

5. Registry loading and execution must continue using the handler-specific validator at both load and execution time.

6. Keep the reviewed registry public API and static handler allow-list unchanged unless absolutely necessary.
